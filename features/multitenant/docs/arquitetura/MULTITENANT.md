# Multi-tenant

Isolamento por **coluna discriminadora** (`tenant_id`) com o `@TenantId` nativo do Hibernate. Um
banco, um schema, e cada linha de dado de tenant carrega o dono.

## Como o tenant da requisição é decidido

O `TenantInterceptor` roda em toda requisição HTTP, depois da autenticação:

| Quem chama | Tenant |
|---|---|
| usuário com linha em `user_tenants` | o tenant dele — o cabeçalho `X-Tenant-Id` é **ignorado** |
| `ROLE_ADMIN` **sem** linha em `user_tenants` (admin da plataforma) | o de `X-Tenant-Id`; sem cabeçalho, **todos** |
| qualquer outro, inclusive anônimo | nenhum (`TenantContext.NONE`) |

`X-Tenant-Id` que não seja número positivo → `400`. Um admin **de tenant** (com vínculo) fica
preso ao próprio tenant como qualquer membro.

## Como tornar uma entidade multi-tenant

```java
@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @TenantId
    @Column(nullable = false, updatable = false)
    private Long tenantId;
    // ...
}
```

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL CHECK (tenant_id > 0) REFERENCES <tabela_do_tenant> (id),
    -- ...
);
CREATE INDEX idx_orders_tenant ON orders (tenant_id);
```

Com isso, e sem nenhuma linha a mais no service ou no repository:

- **toda leitura** filtra pelo tenant atual — JPQL, Specification, derived query **e `findById`**;
- **todo insert** recebe o tenant atual; o código nunca faz `setTenantId`;
- sem tenant definido, nada aparece e o insert quebra no `CHECK (tenant_id > 0)`.

O `CHECK` não é enfeite: é ele que transforma "esqueci de definir o tenant" em erro em vez de
linha órfã gravada com `tenant_id = 0`.

## O que o Hibernate **não** filtra

- **SQL nativo** (`@Query(nativeQuery = true)`, `JdbcTemplate`): escreva o `WHERE tenant_id = ?`
  à mão, com o valor de `TenantContext.current()`. Prefira JPQL.
- **`UPDATE`/`DELETE` em massa via JPQL** (`@Modifying`): confira na change; inclua o tenant na
  condição.
- **Unicidade**: `UNIQUE (email)` numa tabela de tenant é unicidade global. Quase sempre o certo é
  `UNIQUE (tenant_id, email)`.

## Fora de requisição HTTP

O tenant é lido **uma vez, quando a sessão do Hibernate abre** — ou seja, no início da transação.
Defina antes, nunca dentro de um método `@Transactional`.

```java
// job que varre todos os tenants
TenantContext.runAsRoot(() -> orderComponent.expireOverdue());

// job de um tenant específico
TenantContext.runAs(tenantId, () -> orderComponent.recalculate());
```

Scheduler sem `runAs` enxerga **nada** — falha fechada, de propósito.

A porta gRPC (feature `grpc`) **não** define tenant: com as duas features, chamadas gRPC caem em
`NONE` até alguém escrever um `ServerInterceptor` equivalente ao `TenantInterceptor`. Falha
fechada, não vazamento — mas falha.

## Vínculo usuário → tenant

`user_tenants (user_id PK, tenant_id)`: um tenant por usuário. Quem grava é o fluxo de domínio
(ex.: "gerente cadastra corretor na agência") via `UserTenantComponent.assign`. A tabela dona do
tenant (agência, cidade, loja) é **domínio**, não vem do template: crie-a numa migration sua e
acrescente a FK em `user_tenants.tenant_id`.

`users` não é multi-tenant: o login procura o e-mail antes de existir tenant. E-mail é único na
plataforma inteira.

## Por que não `@Filter` num interceptor

Era o desenho do imob. Funciona lá por acaso: o filtro é ligado no `EntityManager` do
interceptor, e só chega à sessão do service porque o *open-in-view* (ligado por default) mantém a
mesma sessão na requisição inteira. Este projeto roda com `spring.jpa.open-in-view=false` — o
filtro seria ligado numa sessão descartável e **não filtraria nada, em silêncio**. E `@Filter`
nunca se aplica a `findById`. O `TenantInterceptorFlowTest` existe para pegar exatamente esse tipo
de regressão: ele atravessa JWT → interceptor → transação → Hibernate.
